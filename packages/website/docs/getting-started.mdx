# Redux Workflow

**One Redux API for queries, mutations, and async workflows.** Built on top of
[Redux Toolkit](https://redux-toolkit.js.org) and
[Redux Saga](https://redux-saga.js.org/).

- **Queries** — cached, deduped reads.
- **Mutations** — writes that invalidate the cache.
- **Workflows** — orchestration: listen to actions, compose queries/mutations, cancel cleanly.

`@redux-workflow/core` is pulled in transitively. `react` and `react-redux`
are peer dependencies — install them only if your project doesn't already
have them.

For a non-React project, install `@redux-workflow/core` instead of
`@redux-workflow/react`.

| Package                         | Description                                                |
| ------------------------------- | ---------------------------------------------------------- |
| `@redux-workflow/core`          | Framework-agnostic. Queries, mutations, workflows.         |
| `@redux-workflow/react`         | React bindings (`useQuery`, `useMutation`, `useWorkflow`). |
| `@redux-workflow/eslint-plugin` | Lint rules (e.g. enforces `yield*`).                       |

## Setup

```ts
import { configureStore, combineReducers } from '@reduxjs/toolkit';
import createSagaMiddleware from 'redux-saga';
import { createApi } from '@redux-workflow/core';

const postsApi = createApi({
  name: 'postsApi',
  queries: (query) => ({
    /* ... */
  }),
  mutations: (mutation) => ({
    /* ... */
  }),
  workflows: (workflow, { queries, mutations }) => ({
    /* ... */
  }),
});

const sagaMiddleware = createSagaMiddleware();

const store = configureStore({
  reducer: combineReducers({
    [postsApi.reducerPath]: postsApi.reducer,
    // ...your other reducers
  }),
  middleware: (getDefault) => getDefault().concat(sagaMiddleware),
});

sagaMiddleware.run(postsApi.rootSaga);
```

Each API mounts its own state subtree at `state[api.reducerPath]`. State is
fully isolated between APIs.

## A first taste

A complete example: a newsletter modal that opens 10 seconds after the user
lands on the homepage — but only if they haven't already subscribed. State,
network calls, and orchestration all live in one api.

```tsx
import { createAction } from '@reduxjs/toolkit';
import { useSelector } from 'react-redux';
import { createApi, httpRequest, delay, put } from '@redux-workflow/react';
import { useMutation } from '@redux-workflow/react';

const onGuestVisitHomepage = createAction('guest/visitedHomepage');
const onGuestLeavesHomepage = createAction('guest/leftHomepage');

// Internal events — declared at module scope, not exported. The workflow
// dispatches them; the slice listens via `extraReducers`. This is the
// canonical pattern for slice writes (see "API slice" in the docs).
const newsletterOpened = createAction('newsletter/opened');
const newsletterClosed = createAction('newsletter/closed');

const newsletterApi = createApi({
  name: 'newsletter',
  queries: (query) => ({
    fetchSubscriptionStatus: query({
      execute: httpRequest<{ subscribed: boolean }, void>({
        method: 'GET',
        url: '/newsletter/status',
      }),
    }),
  }),
  mutations: (mutation) => ({
    subscribe: mutation({
      execute: httpRequest<void, { email: string }>({
        method: 'POST',
        url: '/newsletter/subscribe',
        body: (args) => args,
      }),
      invalidates: ['fetchSubscriptionStatus'],
    }),
  }),
  slice: (slice) =>
    slice({
      initialState: { isOpen: false },
      extraReducers: (builder) => {
        builder.addCase(newsletterOpened, (state) => {
          state.isOpen = true;
        });
        builder.addCase(newsletterClosed, (state) => {
          state.isOpen = false;
        });
      },
      selectors: {
        selectIsModalOpen: (local) => local.isOpen,
      },
    }),
  workflows: (workflow, { mutations, selectors }) => ({
    showModalAfterDelay: workflow({
      listen: onGuestVisitHomepage,
      dismiss: onGuestLeavesHomepage,
      *execute(_, { query, select }) {
        // Read through the cache. Returns { data } | { error }.
        const status = yield* query('fetchSubscriptionStatus', undefined);
        if ('error' in status || status.data.subscribed) return;

        yield* delay(10_000);

        // The workflow ctx exposes `selectors` — use them with `select` to
        // avoid an api self-reference inside *execute.
        const alreadyOpen = yield* select(selectors.selectIsModalOpen);
        if (alreadyOpen) return;

        yield* put(newsletterOpened());
      },
    }),
    closeModalAfterSubscription: workflow({
      listen: mutations.subscribe.on.succeeded,
      *execute() {
        yield* put(newsletterClosed());
      },
    }),
  }),
});

function NewsletterModal() {
  const isOpen = useSelector(newsletterApi.selectors.selectIsModalOpen);
  const [subscribe, { isLoading }] = useMutation(newsletterApi.mutations.subscribe);

  if (!isOpen) return null;

  return (
    <form
      onSubmit={(event) => {
        event.preventDefault();
        subscribe({ email: '...' });
      }}
    >
      <input type="email" name="email" />
      <button disabled={isLoading}>{isLoading ? 'Subscribing…' : 'Subscribe'}</button>
    </form>
  );
}
```

What this example shows working together:

- **Queries cache and dedupe.** `fetchSubscriptionStatus` is read by the
  workflow before it opens the modal. Subsequent reads use the same
  cache entry — only one network call fires.
- **Mutations invalidate.** `subscribe` lists `fetchSubscriptionStatus`
  in `invalidates`, so a successful submission marks the cached status
  stale and the next reader sees fresh data.
- **Slice owns UI state.** `isOpen` lives in the api's slice, declared
  alongside everything else. Writes go through `extraReducers` listening
  to internal events the workflow dispatches.
- **Workflows orchestrate and read.** `showModalAfterDelay` checks the
  cache (via `query`), waits, checks the slice (via
  `select(selectors.x)`), then emits `newsletterOpened`.
  `closeModalAfterSubscription` listens to the mutation's lifecycle and
  emits `newsletterClosed`. See [API slice](/docs/api-slice) for the
  `extraReducers`-listens-to-events pattern in detail.

Continue with [Queries](/docs/queries) for the full picture — caching,
polling, the `{ data }` / `{ error }` contract, and how `async` vs generator
bodies differ.
